# Print API Implementation Plan (PR 3 of 4)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The server side of printing: pair a Mac with one click, let the paired Mac claim queued issues, download them as PDFs and report the result, plus a Printer section in Settings.

**Architecture:**
- Pairing: one-time codes (hashed) handed to the Mac app through a `paperbrew://pair` link. Each paired device gets a long-lived bearer token (hashed).
- `/agent/*` routes authenticate the device, claim issues with `FOR UPDATE SKIP LOCKED`, and render the PDF on download with the brew renderer refactored into a shared function.

**Tech Stack:** Hono, pg, zod, vitest, Node `crypto`, React.

**Spec:** `docs/superpowers/specs/2026-11-22-autonomous-brew-design.md` (section 3 "Pairing", "Agent API", "Articles already in an open issue"; section 4 Printer).

**Depends on:** PR 2 merged (`issues` table, `archive_reason`, `tick()`).

## Global Constraints
- One paired Mac per user: pairing a new one revokes the others.
- Pair code: 8 characters from `ABCDEFGHJKMNPQRSTUVWXYZ23456789`, shown as `XXXX-XXXX`, valid 10 minutes, single use, stored as SHA-256 hex.
- Device token: 32 random bytes, base64url; stored as SHA-256 hex; sent as `Authorization: Bearer <token>`.
- Deep link: `paperbrew://pair?code=<XXXXXXXX>&api=<BETTER_AUTH_URL>`. The Mac app calls `<api>/api/agent/...`; the web proxy strips `/api`.
- `printing` for more than 30 minutes → `failed` with error `timed out`, never back to `queued`.
- At render time, articles archived or deleted since the issue was created are left out. If none are left, the issue becomes `printed` and the PDF route answers 204.
- A successful print archives the issue's still-unarchived articles with `archive_reason = 'printed'`.
- "Print again": `failed` → `queued`, `article_ids` minus any in another `queued`/`printing` issue. If that leaves none, 409.
- Same constraints as PRs 1–2 (tests without DB, phone-first UI, routes behind `requireUser`).

## Review Focus
1. **Two claims race** (the app restarts mid-claim, or there are two instances). One gets the issue; the other gets 204 (Task 2 test `concurrent claim`).
2. **A device removed in Settings while the app is running.** The next call gets 401, and the app stops (Task 2 test `revoked token → 401`).
3. **The PDF download hits `BusyError`** (another brew rendering). Answer 503 with `Retry-After: 30`; the issue stays `printing` for the same device to retry (Task 3 test).
4. **A pair code used twice** (double-click, or the link opened twice). The second use gets 410 and no second device (Task 1 test).
5. **A result reported for an issue this device didn't claim.** Answer 404 and change nothing (Task 2 test).

### Task 2: Claim and result

**Files:**
- Create: `apps/api/src/print/agent.ts`
- Test: `apps/api/test/printAgent.test.ts`

**Interfaces:**
- Consumes: `requireDevice`.
- Produces:
  - `POST /agent/jobs/claim` → 200 `{ id, layout }` | 204. It sets `status='printing'`, `claimed_by`, `claimed_at`.
  - `POST /agent/issues/:id/result { ok: boolean, error?: string }` → 204. Only for an issue with `status='printing'` and `claimed_by` = this device; otherwise 404.
    - ok → `printed`, `printed_at`, and archive its unarchived articles (`archived_at = now()`, `archive_reason='printed'`, `rollover_count = 0`).
    - not ok → `failed`, `error` (≤ 500 chars).

- [ ] **Step 1: Failing tests:**
  - Claim SQL uses `for update skip locked`, picks the oldest `queued` for this device's user, and returns `{ id, layout }`.
  - None → 204.
  - `concurrent claim`: the second returns 204 when the update returns no row.
  - `revoked token → 401`.
  - Result ok runs both updates in one transaction.
  - A result on another device's issue → 404.
  - Bad body → 400.
